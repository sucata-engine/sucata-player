# AGENT.md — sucata-player

## What this is

`sucata-player` is the runtime/engine core of [Sucata](https://sucata.dev), a 2D game engine written in [Odin](https://odin-lang.org/) with [Lua](https://www.lua.org/) as the scripting language (in the spirit of Love2D/Godot). This is the actual executable that loads and plays a Sucata game — analogous to the Love2D runtime or Godot's engine binary. It is driven by the sibling [sucata-cli](../sucata-cli/AGENT.md) tool during development, and gets cloned + bundled with a game's assets to produce standalone distributables.

Key third-party dependencies: [sokol](https://github.com/floooh/sokol-odin) (graphics/app framework + `sokol/audio` raw PCM streaming, shared Odin lib), [odin-http](https://github.com/laytan/odin-http) (shared Odin lib), `vendor:stb/vorbis` (OGG decoding, bundled with the Odin toolchain), lz4 (asset compression), SDL3 (gamepad support), and Lua 5.4 (`vendor:lua/5.4`, `lua54.dll` bundled for Windows distribution). `sokol/audio` itself does no file decoding or mixing — that's all implemented in `src/core/audio/` (WAV decoding is hand-rolled there). **Audio formats: WAV and OGG Vorbis only, no MP3** — an MP3 decoder was tried (vendoring dr_mp3) and dropped for the extra vendored-native-lib complexity it added for one format.

## Packages under `src/`

| Package | Path | Responsibility |
|---|---|---|
| `main` | `src/main.odin` | Entry point. Checks for an embedded build footer (`build.get_build()`) to decide dev-mode vs. packaged-game mode; in dev mode takes a CLI arg (project path or `--version`); wires up `filesystem.init_run_paths` → `lua.init_lua` → `core.main()` (which starts the sokol_app loop). |
| `build` | `src/build/` | Packaged-game detection. Reads the trailing bytes of the running executable for a `SUCATA_BUILD_<hash>` footer appended by `sucata-cli`'s packager; if present, loads `assets.scta` next to the exe, verifies its SHA-256, and boots in bundle mode instead of reading loose files. |
| `common` | `src/common/` | Shared plain-data types with no logic, imported everywhere to avoid import cycles: `Entity` (id, Lua state ref, behaviour ids), `LuaNamespace`/`LuaFunction`, `GraphicObjectProps`/`TextObjectProps`/`ShaderArgs`, `Asset_Archive`/`Asset_Entry`, `EventHandler`, `WindowConfig`, print helpers. |
| `core` | `src/core/` | The engine runtime proper — main loop, scene/entity registry, input, audio, gamepad, timers. See "Core architecture" below. |
| `filesystem` | `src/filesystem/` | Dual-mode asset loading: plain files on disk in dev mode, or entries decompressed on demand from a single LZ4-compressed `.scta` archive in bundle mode. Resolves `src://`/`data://`/`build://` virtual paths. |
| `graphics` | `src/graphics/` | sokol-gfx wrapper: quad/text batching and buffers, camera (view-projection matrix, fixed vs. world-space), texture atlases, fonts, offscreen render target (used for aspect-ratio letterboxing and post-processing), shader loading (including user-supplied shaders from Lua). |
| `lua` | `src/lua/` | The Lua binding layer exposed to games. See "Lua API wiring" below. |
| (generated) | `src/shaders/{post_processing,quad,text}/` | Hand-written `.glsl` shader sources plus machine-generated `.odin` shader-description files (regenerated by `scripts/build-shaders`, cross-compiled to GLSL430/HLSL5/Metal-macOS/WGSL via sokol-shdc). |

## Core architecture (`src/core/`)

**Main loop** (`sokol.odin`): `init_sokol()` runs `sapp.run` with four callbacks:
- `init_callback` — sets up sokol gfx/time, graphics, audio, gamepad; marks `is_game_started`; runs deferred init commands, then runs `init` on every scene entity.
- `frame_callback` — the per-frame loop: updates input/time/audio/gamepad state, `run_update()` (calls `tick` on every entity), renders the scene into an offscreen pass, `run_draw()` (calls `draw` on every entity), applies post-processing, composites to the swapchain (with letterbox/crop per `windowConfig.keep_aspect`), then clears per-frame input state, processes the destroy queue, and steps the Lua GC.
- `cleanup_callback` — fires the registered Lua exit callback (`sucata.window.on_exit`), then tears everything down.
- `event_callback` — forwards OS input/window events.

**Entity/behaviour model** (`entity.odin`, `behaviour.odin`, `core.odin`): an **entity** (`common.Entity`) is a thin struct holding an id, a Lua-registry reference to its `state` table, and a list of behaviour ids. A **behaviour** is just a Lua table with optional `init`/`tick`/`draw`/`free` methods, registered once (keyed by the table's pointer identity) and shared/reused across every entity that references it — so behaviours act like reusable components/scripts, not per-entity copies. `core.odin` holds the global scene registry (`scene`, `global_scene`, `global_scene_map`) and the render queue, which batches quads/text by `RenderGroupKey{texture, z_index, shader, fixed, tiled}` for sorted, batched draw calls.

**Texture lifecycle** (`graphics/images.odin`): images are lazily uploaded to the GPU on first `draw_rect`/`draw_text` call referencing them, and `run_draw()` calls `graphics.destroy_unused_images()` every frame to unload any texture not drawn that frame — keeping GPU memory bounded to what's currently on screen. Textures drawn `graphics.hot_texture_use_threshold` times (runtime var, default 300, exposed to Lua as `sucata.graphic.get/set_hot_texture_threshold`) get their `Image.hot` flag set and are exempt from that per-frame collection from then on, staying resident for the rest of the run — an automatic optimization for frequently-reused textures (UI, atlases) that would otherwise pay repeated reload costs when briefly off-screen. Setting the threshold to `0` disables this use-count-based auto-promotion entirely (checked in `load_image` via `hot_texture_use_threshold > 0`), leaving `preload_image` as the only way to mark a texture hot. `graphics.preload_image` (Lua: `sucata.graphic.preload_texture`) force-loads a texture and sets `hot` immediately regardless of the threshold; it's routed through `core.add_post_command`/`PostPreloadTexture` when called before `core.is_game_started`, same as `load_shader`.

**Events** (`events.odin`): a simple pub/sub keyed by an FNV-64a hash of the event name, backing the Lua `sucata.events.on`/`sucata.events.emit` API.

**UI** (`microui.odin`): wraps `vendor:microui` for the `sucata.ui` immediate-mode widgets. `mu_ctx: mu.Context` is the single global microui context; `microui_begin_frame`/`run_draw`/`microui_end_frame` bracket the per-frame widget-building calls (inside the offscreen pass in `frame_callback`), and `microui_render` walks the resulting command list and draws it with `sokol_gl` (own blended `mu_pipeline`, since sokol_gl's default pipeline has no alpha blending) into the swapchain pass, on top of postfx. The default microui bitmap font/icon atlas (`mu.default_atlas_alpha`, 128×128, alpha-only) is uploaded once as an RGBA8 texture (white RGB + atlas alpha) so glyph color comes from the vertex color, not the texture. Per-widget style overrides (`Mu_Style`: x/y/width/height/text_size/color/background_color/border_color) snapshot-and-restore `ctx.style^` around each call; `text_size` is the odd one — since `mu.Command_Text` only carries a `font: Font` (`distinct rawptr`) through untouched from call-time to render-time, the scale is fixed-point-encoded into that pointer (`microui_font_for_scale`/`microui_scale_from_font`) instead of using a real font. Checkbox/slider/textbox need a stable memory address across frames for mu's own id-by-pointer scheme, so their state is heap-allocated once per Lua-supplied `id` string (`mu_bool_state`/`mu_real_state`/`mu_text_state` maps), not stack-local. The "root" (`microui_root_begin`, a full-screen borderless window) pins its `zindex` to `0` every frame — otherwise, since it overlaps the whole screen, a single click anywhere would `bring_to_front` it above real windows and permanently steal their hover/click (a real bug hit during development). It's not exposed to Lua directly: `microui_ensure_root` (called by every leaf widget — label/text/button/checkbox/slider/textbox) lazily begins it the first time a widget is drawn while `mu_open_container_depth == 0` (i.e. no `draw_window`/`draw_popup` is currently open), tracked via `mu_root_open`, and `microui_end_frame` closes it (before `mu.end()`) if it was ever opened that frame — so Lua code never has to open/close it itself, and calling `mu.begin_window` for the same root container twice in one frame (which corrupts mu's root-container jump-chain) never happens. `draw_window`/`draw_popup` follow vanilla microui's own contract: callers must call the matching `end_*` if and only if the `draw_*` returned `true` — there's no bookkeeping stack on our side (an earlier version tried one and it corrupted mu's own container stack the moment a conditionally-open container, like a popup, was closed most of the time); `mu_open_container_depth` is incremented/decremented by `microui_window_begin`/`end`/`microui_popup_begin` purely to gate the root auto-open, not for that bookkeeping. Every Lua-facing entry point (`microui_window_begin/end`, `microui_popup_open/begin`, and all six leaf widgets) starts with `microui_guard_draw_step()`, which checks the same `is_draw_step` flag `core.add_to_render_queue` already guards `sucata.graphic` draw calls with, logs an error, and no-ops if called outside `run_draw()`.

The `audio` subpackage (`src/core/audio/`, package `audio_engine`) is its own mixer built on top of the raw `shared:sokol/audio` PCM stream: file decoding (`decode.odin`, `wav.odin` — WAV and OGG Vorbis only), resampling/pitch, per-sound and per-group volume/pitch, looping, and mixing (`engine.odin`). It can't import `core` back (that would be a cycle, since `core/sokol.odin` imports it), so it keeps its own captured `runtime.Context` (`engine_context`) instead of using `core.DEFAULT_CONTEXT`.

Other `core/` files worth knowing: `gamepad.odin`/`input.odin` (SDL3 + keyboard/mouse), `timer.odin`, `screen.odin`, `hover.odin`, `cursor.odin`, `icon.odin`, `config.odin` (`windowConfig`), `init_queue.odin` (one-shot deferred Lua callbacks, e.g. `on_init`), `arena.odin` (per-frame temp allocator, reset every frame), `post_commands.odin`, `tags.odin`.

## Lua API wiring (`src/lua/`)

One subpackage per module exposed to Lua games: `audio/`, `camera/`, `events/`, `file_system/`, `gamepad/`, `graphic/`, `input/`, `math/`, `scene/`, `system/`, `time/`, `ui/`, `window/`. Inside each, one file per bound function, plus a `<module>.odin` that declares a `<MODULE>_NAMESPACE: lua_common.LuaNamespace{name, functions}` listing them all. (These modules are what's documented for game developers in the sibling `docs/` repo, under `docs/docs/references/sucata.*.md` — keep that documentation in sync with this directory when the API changes.)

`ui/` (`sucata.ui`) is the odd one out: every bound function there takes exactly one table argument (see `lua/ui/utils.odin`'s `get_style_from_table`/`get_table_color` helpers), unlike the positional-arg style used elsewhere (e.g. `sucata.camera.set_camera_position(x, y)`).

`lua.odin` is the wiring hub:
- `lua_namespaces` — master list of every `LuaNamespace`.
- `create_namespaces(L)` — builds the global `sucata` Lua table with one subtable per namespace (`sucata.audio`, `sucata.scene`, ...) plus `sucata.meta` (`OS`, `VERSION`).
- `init_lua(path)` — creates the Lua state, installs a panic handler, opens stdlibs, calls `create_namespaces`, installs a `custom_loader` package searcher (so `require("foo.bar")` resolves against `src://foo/bar.lua` or the asset archive, supporting both `.lua` and `/init.lua`), loads and runs the game's entry chunk, and configures the incremental GC.

**`src/lua/lua_common/`** — shared helpers used by every binding function:
- `utils.odin` — typed table-field extraction (`get_table_number`, `get_table_string`, `get_table_boolean`, `get_table_ref`, ...) and argument validation (`validate_arg_count`, `validate_number`, `validate_string`, `validate_table`, `validate_function`, ...) that every bound function calls first, raising a Lua error via `lua.error` on failure.
- `entity.odin` — converts a Lua entity-definition table into a `common.Entity` (`lua_table_to_entity`, `create_entity_by_lua`), including deep-copying the `state` subtable and deduping/registering behaviour tables by pointer identity.
- `shaders.odin` — parses a Lua `shader_args` table into `common.ShaderArgs` (numbers, strings, 2/3/4-float vectors), used by `sucata.graphic.set_post_processing_args` and draw calls.

When adding a new Lua-exposed function: add a new `.odin` file in the relevant `src/lua/<module>/` directory following the existing `LuaFunction` pattern, register it in that module's `<module>.odin` namespace list, and update the matching `docs/docs/references/sucata.<module>.md` (and ideally `sucata-lua-addon/library/sucata/<module>.lua`) in the sibling repos.

## Dev workflow

1. Install Odin (version pinned in `README.md`, currently `dev-2026-04-nightly:a896fb2`).
2. `./scripts/install-shared/unix.sh` (or `win.ps1`) — clones `sokol-odin` (as `sokol`) and `odin-http` (as `http`) into Odin's `shared:` collection.
3. Build: `./scripts/build-debug/unix.sh` (debug + ASan) or `./scripts/build-release/unix.sh` (optimized). Both invoke `odin build src/ -out:sucata-player [...]`.
4. If you edit any `src/shaders/*/*.glsl`, regenerate the matching `.odin` file with `./scripts/build-shaders/unix.sh` (invokes `sokol-shdc`) before rebuilding — the `.odin` shader files are generated output, not hand-edited.
5. Run a game directly with `./sucata-player <path-to-game>`, or via `sucata run <file>` from the sibling `sucata-cli`.
